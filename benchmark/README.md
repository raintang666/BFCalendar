## 2026-11-26 STK 首页全屏拉伸的 Raster 复测

在应用入口 `CalendarViewFlutterApp → CalendarDemoPage` 上测试，保留当月角标、工具栏和下方卡片。主对照使用华为 STK-TL00、Android 10、60 Hz、Mali-G51 和默认 Impeller OpenGLES。物理屏为 1080 × 2340，测试时系统已有的显示覆盖为 1125 × 2436，DPR 为 3。基线是上一轮按行缓存矢量指令的工作区版本。

### Android 系统滑动

两版均为相同 Flutter SDK 和依赖的 Android ARM64 Profile 构建，运行时检查 `kProfileMode`。按改前、改后、改后、改前启动四次，每次在真实首页下拉 8 次。主对照的 32 次滑动均从屏幕坐标 (563, 762) 出发，由 Android 输入系统在 400 ms 内下拉 1200 个屏幕像素。每次采集都校验日历最终高度等于可用视口高度。表内按所有有效手势的原始帧合并计算，未开启系统 trace。

| 版本 | 手势数 | UI P95（ms） | Raster P95（ms） | Raster P99（ms） | 超预算帧 / 总帧 | 超过两帧预算 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 上一版 | 16 | 4.04 | 20.85 | 28.79 | 126/370（34.0%） | 2 |
| 本次 | 16 | 3.68 | 19.39 | 21.04 | 100/326（30.7%） | 0 |

每次手势平均超预算帧从 7.88 降到 6.25，首次采样帧的 UI 耗时中位数从 14.37 降到 5.37 ms。触及全屏上限后，继续向下拖动会产生相同的布局，本次略去这部分重建，因此两版采样帧数不同。超预算指 UI 或 Raster 任一阶段超过 16.67 ms，每帧只计一次。两轮改后均有接近或超过预算的帧，P95 仍在阈值以上。

另外各做 8 次系统滑动，读取 Android SurfaceFlinger 的实际呈现时间。取首个新画面起 200 ms 的连续移动阶段，超过 25 ms（1.5 个刷新周期）的相邻呈现间隔从 2/94 变为 0/96。这个小样本只覆盖拖动前段，和 Flutter 绘制阶段的超预算计数是两个不同指标。

### Raster 时间花在哪里

在与上一轮相同的简化首页基准中，另取三次手势作 Android 系统 trace。从逐日绘制切换为记录矢量行之后，全部采样帧的 `dequeueBuffer` 中位耗时从 2.12 增至 5.84 ms，`LayerTree::Paint` 中位耗时两版均为 0.06 ms。真实首页上一版单独录制的 88 帧里，22 个 Raster 超预算帧的 `dequeueBuffer` 中位耗时为 8.41 ms，其余 66 帧为 4.62 ms。这个调用在 GLES 提交过程中获取下一块显示缓冲区，耗时包含等待。慢帧主要多花在这里，trace 无法进一步区分 GPU 完成前序工作和显示队列释放缓冲区各占多少。

本次在可见月份首帧绘制后，将支持的行内容预绘到一张设备分辨率纹理。拖动和吸附期间用一次 `drawAtlas` 提交各行的新位置，静止时按矢量绘制。每个交互日历最多持有一张纹理，上限 1,572,864 像素，收到内存压力通知时释放。大字号、窄日期格和混合自定义 Widget 使用原有绘制路径。对应真实首页 trace 的 `dequeueBuffer` 中位耗时从 6.14 降至 5.60 ms。trace 独立采集，提交、绘制和缓冲区调用存在嵌套，耗时不能相加。

### 复测完整首页

## 2026-11-26 全屏拉伸时的日期格重绘

全屏拉伸会逐帧改变月视图的行高。默认日期的数字和选中圆形跟随行中心移动，首页样式的日期、农历和角标跟随行顶移动，分割线跟随行底移动。现在首次拉伸时按行记录这些矢量绘制指令，后续帧只更新位置。行高不足以容纳内容时，沿用按实际尺寸绘制的路径。需要根据高度绘图的自定义画笔和 Widget 也继续接收实际尺寸。

在 2026 年 2 月的 28 个可见日期上，连续拖动 8 帧，默认样式的日期画笔调用从 **224 次降到 0 次**。加入一个自定义 Widget 后，从 **224 次降到 8 次**，每帧只重绘这个格子。计数覆盖连续拖动阶段，真机帧耗时包含进入拉伸和手势结束时的动画。
